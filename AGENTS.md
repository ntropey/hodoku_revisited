# AGENTS.md

Guidance for AI coding agents (and humans) working in this repository. Read this before making
changes.

## What this is

Hodoku Revisited is a modern TypeScript port of **HoDoKu 2.2.0** (Bernhard Hobiger's Sudoku
generator, solver, trainer and analyzer, 2008–12). The goal is to match the original solver's
behavior exactly while giving it a new web UI. Licensed **GPL-3.0-or-later**.

## Repository layout

pnpm workspace, Node >= 20 (CI and the site build use Node 22), TypeScript, ESM throughout.

- `packages/core` — the engine. Pure TypeScript: **no DOM, no Node APIs.** Board model, solver,
  generator, text formats.
- `packages/app` — the PWA (React 18 + Vite). The app UI; runs the solver/generator in a Web Worker.
- `packages/website` — a dependency-free static site generator (plain `.mjs`). Technique guides plus
  the app copied to `/play/`.
- `docs/` — `PORT-PLAN.md` (status and roadmap), `LICENSE-AUDIT.md`, `design/`.

## Common commands

Run from the repository root:

```sh
pnpm install
pnpm typecheck                                    # tsc across packages; node --check for the website
pnpm test                                         # every package
pnpm --filter @hodoku/core test
pnpm --filter @hodoku/app test
pnpm --filter @hodoku/app dev                     # dev server
pnpm --filter @hodoku/app build                   # tsc + vite build -> packages/app/dist
pnpm --filter @hodoku/website build               # site, including the app -> packages/website/dist
pnpm --filter @hodoku/website test                # builds the site, then asserts on the output
```

`SITE_URL=https://hodokurevisited.com/` is set in CI for the website build (it writes `sitemap.xml`
and `robots.txt`). The core golden tests take a couple of minutes; run the full `pnpm test`.

Before finishing a change, run `pnpm typecheck` and `pnpm test`, and the affected package's `build`.
`pnpm install` may print `ERR_PNPM_IGNORED_BUILDS` for `esbuild`; that is expected here.

## Architecture notes

- **The solver must match HoDoKu.** `packages/core` is verified step by step against the original
  Java solver with golden tests (`packages/core/test/golden*.test.ts`, `findall.test.ts`). Never
  change solver output, step ordering or scoring to make a test pass — treat a golden diff as a bug
  in your change.
- **App/worker split.** The app talks to the solver through `packages/app/src/solverClient.ts` →
  `worker.ts` → `solverApi.ts`. Keep `solverApi.ts` pure and testable; keep the message shapes in
  `protocol.ts` in sync across all three.
- **Game logic is pure.** `packages/app/src/game.ts` is pure and unit-tested; keep UI concerns out of
  it.
- **The website is generated.** `packages/website/src/build.mjs` writes every page from string
  literals and emits no separate JS assets (scripts are inlined, e.g. `gate.mjs`, `consent.mjs`).
  `/play/` is the app's own Vite build copied verbatim — never add site-only scripts or banners to
  the app.
- **The manual documents the app.** `packages/website/src/manual.mjs` must be kept in step with the
  app's behavior.

## Do not edit generated files

- `packages/core/src/generated/*` (`defaultSteps.ts`, `solutionType.ts`) — generated by
  `scripts/gen-tables.py` from the original source.
- `packages/app/scripts/gen-bank.mjs`, `packages/website/scripts/gen-examples.mjs` — bundled by
  esbuild from the adjacent `.ts` (gitignored; rebuild with `gen-bank:build` / `gen-examples`).
- `packages/app/src/bank/bank.json` (from `merge-bank.mjs`), `packages/website/src/examples.json`
  (from `gen-examples.ts`).

Edit the sources, not these outputs.

## Coding conventions

- TypeScript `strict` (see `tsconfig.base.json`). Prefer named exports.
- Style: **2-space indent, single quotes, semicolons.** No Prettier or ESLint is configured — match
  the surrounding code, and keep comments purposeful.
- No new runtime dependencies without a clear reason; the website is deliberately dependency-free.
- UI text is plain English for now (i18n is planned but not implemented).

## Tests

- `packages/core` and `packages/app` use Vitest.
- `packages/website` uses Node's built-in test runner (`node --test`); it builds the site and asserts
  on the generated HTML.
- Add tests with behavior changes. CI runs the whole suite.

## Git and pull requests

- **`main` deploys.** Every push to `main` runs `.github/workflows/pages.yml` and publishes to
  https://hodokurevisited.com/. Do not commit or push to `main` directly.
- Work on a branch and open a pull request. CI (`.github/workflows/ci.yml`) runs `pnpm typecheck`,
  `pnpm test`, and the app and website builds on every push and PR.
- Use a short, descriptive branch name (recent examples: `hint-technique-settings`,
  `consent-banner`, `legacy-captures`). Commit subjects read `Area: summary`, lowercase after the
  colon (e.g. `App: …`, `Website: …`, `Docs: …`).

## Documentation and licensing

- Keep `docs/PORT-PLAN.md` (status and backlog), `README.md`, and the website manual truthful as
  things land.
- Licensing is audited in `docs/LICENSE-AUDIT.md`. Keep the source headers, and do not copy original
  data sets, the original logo or icons, or the GFDL manual text — write new equivalents. New code
  stays GPL-3.0-or-later.
